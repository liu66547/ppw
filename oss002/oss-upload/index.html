Strengths

个人优势

四个维度：前三块是现在能交付什么，第四块是以后能走多远。 每一条都能用项目里的代码、数字和证据核对，不是自我评价。

01 · 测试思维

能判断"测到位了没有"，而不只是"跑通了"

把「怎么防止用例假绿」变成硬约束，而不是靠自觉

  • 过滤场景坚持阳性 / 阴性双侧证据 —— 只验证一侧的用例，本质上什么都没证明
  • 区分契约型与记录型断言：主键唯一查询断言"恰好一条"是契约；对系统数据现状锁定为记录型并告警
  • 禁止条件断言、禁止裸字面量，从机制上杜绝用例静默通过

02 · 框架设计

能把重复劳动变成可复用资产

从零设计四层架构，不是照着教程改

  • 用例层 / 接口层 / 造数层 / 基础层职责分离，接口变更只需改 Api 类、用例零感知
  • 造数层支持 subject → question → paper → task 逐级组合，消除对任何环境预置数据的依赖
  • 用 Page Object 让 UI 用例与页面元素解耦，页面改版只需维护定位层

03 · 工程化落地

测试结果可复现、可验收、能进流水线

数据自己造、自己清、自己对账；CI 真实在跑

  • 栈式清理把"下游先删、上游后删"内化进数据结构，不依赖人的记忆力
  • 统一 zz_ 前缀 + 时间戳保证数据唯一，执行后用 SQL 对账验收零残留
  • Jenkins 参数化流水线 + 定时回归 + Allure 报告归档 + 失败邮件告警，失败与恢复都有通知

04 · 持续学习与主动性

没人教的部分，自己把它学会

从零补技术栈，遇到问题挖到根因

  • 这一整套技术栈（RestAssured / Jenkins / Allure）都是课外自学的，没有课程要求
  • 定位缺陷时会读后端源码：顺着异常堆栈找到具体代码行，而不是只报一个 500
  • 主动挖掘而非等待分配 —— 系统级一致性问题和孤儿数据都是我主动测出来并留证的
