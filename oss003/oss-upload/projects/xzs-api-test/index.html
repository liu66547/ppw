项目背景

被测系统：学之思开源考试系统（xzs）—— 基于 Spring Boot 的在线考试系统，含管理端与学生端。

测试范围：管理端 REST API，6 个模块、21 个接口 —— 登录 / 登出、学科、题目、任务、试卷、答卷。

要解决的问题：接口自动化最常见的失败模式不是”跑不起来”，而是跑绿了但什么都没测到。数据依赖环境预置、断言写死期望值、执行完留下一地脏数据 —— 这样的用例越多，可信度反而越低。

所以这个项目的目标不是”把 21 个接口跑一遍”，而是建立一套让绿灯可信的机制。

核心成果：环境依赖 0（测试数据由用例现场自造，clone 后可直接运行），数据残留 0（全套执行后 zz_% 前缀 SQL 对账为空）。

四个关键设计决策：

  1. 接口层与用例层解耦 —— 接口变更只需修改 Api 类，用例零感知。这是”框架”和”一堆脚本”的分界线。

  2. CleanupRegistry 栈式清理 —— 按”造数即注册”顺序入栈，@AfterMethod / @AfterClass 逆序执行。 天然满足”下游先删、上游后删”的依赖顺序：把规则内化进数据结构，而不是要求每个人记住规则。

  3. 造数链自给自足 —— CreateData 支持 subject → question → paper → task 逐级组合， 已消除对任何环境预置数据的依赖。例如 task 用例现场自造”学科 → 题目 → 试卷 → 任务”全链。

  4. 参数化环境 —— base.uri 通过 -Dbase.uri= 注入，本地 / 测试 / 预发一键切换，一套用例多环境执行。

测试设计原则

这部分是本项目真正的产出 —— 规范写进了框架机制，而不是停在文档里。

  • 过滤验证黄金法则：每个过滤条件必须给出”阳性（该来的来了）+ 阴性（不该来的没来）“双侧证据。 只验证一侧的用例，本质上什么都没证明。

  • 契约型 vs 记录型断言：主键唯一查询断言”恰好一条”（契约型）；对系统数据现状（如答卷表为空） 采用记录型断言锁定现状 —— 现状变化即产生告警，而不是假装它是契约。

  • 同通道对照：删除 / 编辑前后的对照必须走同一查询通道、同一参数口径，避免口径差异导致假绿。

  • 禁止条件断言：断言不允许藏在不被验证的 if 条件里 —— 前提破坏时用例会静默通过。

  • 禁裸字面量：断言中的期望值必须来自变量或本用例刚造的数据，杜绝与环境数据巧合耦合。

  • 数据治理规范：测试数据统一 zz_ 前缀 + 时间戳保证唯一； 执行后以 SQL 对账（zz_% 且 deleted=0 应为空）验收清理效果。

缺陷候选（可复现）

#描述证据
1编辑不存在的资源，错误处理三极不一致：学科编辑静默返回”成功”；试卷编辑直接 NPE 500；无明确业务错误码实测 + 后端堆栈
2引用完整性校验缺失，异常延迟到”使用点”以 500 崩溃：任务引用不存在的试卷、试卷引用不存在的题目 / 学科等4 组堆栈（如 savePaperFromVM:105、levelBySubjectId:47 NPE）
3关键枚举 / 值域零校验：questionType=999、gradeLevel=999 等非法值静默入库实测
4同类字段空值校验不一致：多选题 items 为空 → 500 兜底；单选题 items 为空 → 接受对照实测
5删除后文本内容表（t_text_content）残留孤儿数据SQL 实证
6错误信息质量三级并存：字段级精准 501 / 框架级 500 / 静默成功 —— 同一系统三张脸全程采集

系统级一致性观察

  1. “已删过滤”三层不统一：分页查询过滤已删；按 id 查询（select）不过滤已删；联表读取不过滤已删 （软删试卷仍可被任务引用并读回）。学科 / 题目 / 任务 / 试卷四模块均复现。
  2. 请求 / 响应共用 DTO：响应中的只读派生字段（如任务 paperItems.name、frameTextContentId） 在契约上表现为”可填”，实际写入被忽略。
  3. 主键查询 SQL 不带 deleted 过滤（selectByPrimaryKey 系列）。

设计特性确认（经实验验明为正身，避免误报）

发现不等于缺陷。以下是我验证后排除的项 —— 先把它们排除掉，才能让真正的缺陷报告有分量：

  • 引用 + 派生结构家族：paperItems / questionItems 中唯一有效字段为 id，其余字段读时联表派生；
  • 可变性图谱：question 的 questionType / gradeLevel 不可改（静默忽略），title / subjectId / correct 可改； paper 全字段可改（含换学科并重算 level、换题）；task 可换试卷；
  • 写时类型宽容：score 传数字 / 字符串均可；
  • 软删数据可被引用：如题目可引用软删学科。

值得肯定的设计

如实记录系统做得好的地方，也是测试报告的一部分：

  • 501 字段级校验文案精确到字段路径（如 titleItems[0].questionItems[0].score : 不能为空）—— 错误信息标杆；
  • 事务兜底：编辑中途异常自动回滚，不留半截脏数据；
  • 分页输出结构全站统一（MyBatis 分页插件），空集形状一致。
如何运行（前置条件、命令与数据对账 SQL）

前置条件：JDK 8+、Maven 3.x、本地已启动的 xzs 服务（默认 http://localhost:8000）及 MySQL。

# 全量执行（默认 base.uri = http://localhost:8000）
mvn clean test

# 指定被测环境
mvn clean test -Dbase.uri=http://test.example.com:8000

# 单模块执行
mvn test -Dtest=TaskTest

# 查看 Allure 报告
allure serve target/allure-results

数据对账（执行后应全部为 0 行）：

SELECT id FROM t_subject    WHERE name  LIKE 'zz_%' AND deleted = 0;
SELECT id FROM t_question   WHERE title LIKE 'zz_%' AND deleted = 0;
SELECT id FROM t_exam_paper WHERE name  LIKE 'zz_%' AND deleted = 0;
SELECT id FROM t_task_exam  WHERE title LIKE 'zz_%' AND deleted = 0;

持续集成与测试报告

Jenkins Declarative Pipeline（仓库根目录 Jenkinsfile）：

  • 参数化构建：BASE_URI 下拉多环境选择（本地 / 测试 / 预发），一套用例多环境执行；
  • 触发策略：SCM 轮询（每小时）+ 夜间定时构建（每日）；
  • 构建与测试：mvn clean test -Dbase.uri=${BASE_URI}；
  • 报告归档：JUnit 结果（Surefire XML）与 Allure 报告自动发布； Allure 报告同时打包为构建工件（allure-report.zip）可直接下载；
  • 通知：构建失败发送告警邮件；由失败恢复正常时发送恢复通知（状态未变化不打扰）。

最近构建：#20 全绿 —— 35 条用例 0 失败，Allure Report 与 Tests 结果页均已归档。

Allure 报告：按 Epic / Feature / Story 分层组织，标注 Severity。
