TL;DR · 30 秒看懂

页面改版时只需要改定位层，用例层一行不动。

  • 定位与断言彻底解耦：BasePage 收口所有元素查找，页面类只声明「有什么元素、能做什么」，用例层只写业务断言
  • 多定位符兜底：CSS 优先、XPath 兜底，每一轮轮询都从第一个定位符重试，单个定位符失效不会拖垮整条等待
  • 零 sleep：所有等待都走显式条件（元素可见 / 可点击 / URL 变化 / 新窗口句柄出现），不做固定时长硬等
  • 结果可复核：失败自动截图接入 Allure，`testFailureIgnore=false` 保证「通过率」这个数字不被掩盖

项目背景

被测系统：B 站 Web 端（动态渲染的现代前端应用，且搜索结果会在新窗口打开）。

要解决的问题：UI 自动化最容易烂在两件事上 ——

  1. 页面改版就全崩：定位写死在用例里，页面一改，所有用例一起红；
  2. 动态渲染带来的假失败：元素还没渲染就去点，报错但其实是等待策略没写对。

所以这个项目的重点不在”覆盖多少条用例”，而在把定位与用例解耦、把等待做成框架能力， 让用例数量增长时不会同时带来维护成本的增长。

元素查找：多定位符兜底

BasePage#find(By...) 是整个框架最核心的一段，它同时解决四个问题：

  1. CSS 优先、XPath 兜底 —— 每次轮询都从第一个定位符重新试，不记住”上次是谁失败的”， 因为页面是动态的，某个定位符可能这一轮没渲染出来、下一轮就有了；
  2. 过滤不可见元素 —— 遍历结果找第一个 isDisplayed() 的，而不是直接取 get(0)： DOM 里可能有隐藏的同名节点（模板、占位），第一个不一定可见；
  3. 单个定位符出错不影响整体 —— 按定位符 catch InvalidSelector / NoSuchElement / StaleElement， 继续试下一个，这才叫兜底；
  4. 超时信息可读 —— 重写 TimeoutException，把这次依次尝试过的定位符全部打印出来， 否则 lambda 条件下只会看到一串 lambda 地址，根本不知道是哪个定位符挂了。

等待策略

全项目没有一处固定 sleep，等待全部是显式条件：

  • 元素可见 / 可点击 —— visibilityOfElementLocated、elementToBeClickable
  • URL 变化 —— 用户 Tab 点击后轮询 getCurrentUrl().contains("/upuser")
  • 新窗口出现 —— 搜索会在新窗口打开结果页，先记下句柄集合，再等”多出来的那个句柄”出现

等待上限由 explicit.timeout=15 秒统一控制，改配置不改代码。

用例隔离

BaseTest 用 @BeforeMethod 建驱动、@AfterMethod(alwaysRun = true) 关驱动 —— 每条用例一个干净浏览器会话，且失败时也一定会关闭，避免残留进程拖垮后续用例。

用例覆盖

当前 3 条核心用例，覆盖「页面能打开 → 核心交互能用 → 异常输入有正确反馈」这条主干：

用例验证点耗时
homePageShouldLoad首页「番剧」频道入口可见，且 URL 落在 bilibili.com 域内1.34s
searchShouldLoadSearchPage首页输入关键词回车 → 自动切到搜索结果新窗口 → 结果页 Tab 栏渲染完成2.46s

第三条是阴性用例：它验证的不是”能搜到”，而是搜不到的时候界面给了正确的反馈。 阳性用例证明功能可用，阴性用例才证明”没结果”和”坏了”是两件不同的事。

Allure 侧同步产出 3 条 passed 结果，失败截图机制在这个前提下保持待命 —— 它只有在真的失败时才会留下现场，所以成功跑批时报告里是干净的。

设计取舍

  • 为什么用例范围限定在免登录流程：B 站登录有风控（滑块 + 设备校验）， 把登录写进用例会让整个套件的稳定性依赖第三方风控策略， 所以主流程刻意避开登录，换取”任何时候跑都能过”。
  • 为什么 Allure 停在 2.x：本机 Allure CLI 是 2.46，Allure 3 换了报告生成架构， 2.x 的结果目录不能被 3.x 直接渲染 —— 依赖版本要和本机工具链对齐，而不是和官网最新对齐。
  • 为什么并行度先设为串行：并行会放大 driver 共享、截图、窗口句柄互相干扰的问题， 等用例本身稳定后再开并行才有意义。
