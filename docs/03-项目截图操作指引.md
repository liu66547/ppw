# 项目截图操作指引

> 截图是这个网站**最有说服力的部分**。纯文字说「我做了 35 条用例」是自述；
> 一张 Allure 报告截图是证据。面试官点开你 GitHub 之前，先看到的就是这些图。

---

## 一、该截哪几张（按优先级）

### 🔴 必截（这三张最能打）

| # | 截什么 | 怎么截 | 为什么重要 |
| --- | --- | --- | --- |
| 1 | **Allure 报告总览** | `allure serve target/allure-results`，截 Overview 页（含 Total/Passed/Failed/Pass rate + Behaviors 分层树） | 一眼看到「35 条用例 0 失败」和 Epic/Feature/Story 分层 —— 这证明你会用专业报告工具，不是打印日志 |
| 2 | **Jenkins 构建历史** | Jenkins 项目页 → Build History，截到 #20 绿色勾 | 证明 CI 是真的在跑，不是你本地手动执行然后写「已接入 CI」 |
| 3 | **缺陷证据** | 缺陷 1 或 2 的后端异常堆栈（如 `savePaperFromVM:105` 那个 NPE 的 500 响应 + 日志） | **这是最能体现测试深度的一张** —— 大部分实习生只会写「接口返回 500」，你能给出堆栈定位到代码行 |

### 🟡 加分（有就放，没有不影响）

| # | 截什么 | 说明 |
| --- | --- | --- |
| 4 | **SQL 对账结果** | 执行那 4 条 `zz_%` 对账 SQL，截全为 0 行的结果 —— 证明「数据零残留」不是口号 |
| 5 | **项目目录结构** | IDE 里的四层分层目录树（api/common/data/test）—— 一眼看出架构，比文字描述直观 |
| 6 | **Jenkinsfile 内容** | 参数化构建 + 报告归档那几段 —— 证明流水线是你写的 |
| 7 | **Allure 的 Suites 页** | 按测试类分组的执行时长 —— 体现用例组织 |

### ⚪ UI 自动化项目（等你的项目优化完）

- Selenium 失败自动截图的**截图产物**（这个特别加分，因为它是「测试工程能力」的直接体现）
- Allure 报告里的失败现场图
- Page Object 分层代码结构

## 二、怎么截图才专业

**几个细节，做和不做差很多：**

1. **窗口宽度 ≥ 1400px**，别用手机截图当桌面报告用
2. **缩放比调到 125% 或 150%**（浏览器 `Ctrl` + `+`）—— 否则报告里的字在网页上会小到看不清
3. **裁掉无关部分**：浏览器地址栏、书签栏、任务栏、其他标签页都裁掉
4. **深色模式下截最好**（Allure 支持切换），和网站风格更搭，也更清晰
5. **文件名用英文小写加连字符**：`allure-overview.png` 而不是 `截图1.png`
   —— 中文文件名在部署时容易出编码问题

**DevTools 高级技巧**（推荐）：
按 `F12` → `Ctrl+Shift+P` → 输入 `capture full size screenshot`
可以截取**整个可滚动页面**，比手动拼接干净。

## 三、怎么把截图挂到网站上

### 第 1 步：把图片放进项目

放到 **`public/projects/`** 目录：

```
public/
└── projects/
    ├── allure-overview.png
    ├── jenkins-builds.png
    ├── defect-stacktrace.png
    ├── sql-reconciliation.png
    └── project-structure.png
```

> 💡 图片建议控制在 **500KB 以内**。太大的话用 https://squoosh.app 压缩一下
> （选 WebP 格式，质量 80，能压掉 70% 体积还不糊）。

### 第 2 步：在项目 Markdown 里登记

打开 `src/content/projects/xzs-api-test.md`，在开头两个 `---` 之间的
**frontmatter** 区域，找到（或添加）`screenshots:` 段落：

```yaml
screenshots:
  - src: /projects/allure-overview.png
    alt: Allure 测试报告总览，35 条用例全部通过
    caption: Allure 报告按 Epic / Feature / Story 分层组织，35 条用例 0 失败 —— 这比「我写了 35 条用例」有说服力得多。
    group: 测试报告

  - src: /projects/jenkins-builds.png
    alt: Jenkins 构建历史，#20 构建全绿
    caption: Jenkins Declarative Pipeline 参数化构建，支持本地/测试/预发三套环境一键切换；失败自动邮件告警。
    group: 持续集成

  - src: /projects/defect-stacktrace.png
    alt: 编辑不存在的试卷时后端抛出 NPE 并返回 500
    caption: 引用完整性校验缺失，异常延迟到「使用点」才以 500 崩溃 —— 后端堆栈精确定位到 savePaperFromVM:105。
    group: 缺陷证据
```

### 第 3 步：字段含义

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `src` | ✅ | 图片路径，**以 `/` 开头**，对应 `public/` 目录。`public/projects/a.png` → `/projects/a.png` |
| `alt` | ✅ | 图片的文字描述（无障碍用；图片加载失败时会显示） |
| `caption` | 建议填 | **图注 —— 这个最关键**。不要写「Allure 报告」，要写「这张图证明了什么」 |
| `group` | 可选 | 分组名。**连续的、group 相同的图会被归到同一个小标题下** |

### 第 4 步：预览

```powershell
.\preview.ps1
```

浏览器打开项目详情页，滚到底部就能看到「项目截图」板块。
**点击任意一张可以放大**（Allure 报告字小，必须能放大看）。

## 四、图注怎么写（决定性细节）

**❌ 差**：`Allure 测试报告`
—— 面试官自己会看，你等于什么都没说

**✅ 好**：`Allure 报告按 Epic / Feature / Story 分层组织，35 条用例 0 失败 —— 分层结构让失败用例能直接定位到具体业务模块`
—— 说清了**这是什么** + **为什么要这样做**

**图注公式**：`这是什么` + `关键数字/结论` + `这么做的用意`

再给两个例子：

- ❌ `Jenkins 构建截图`
  ✅ `Jenkins 参数化构建历史，#20 全绿。#{BASE_URI} 下拉切换三套环境，一套用例多环境执行；失败自动发邮件告警`

- ❌ `缺陷截图`
  ✅ `编辑不存在的试卷 → 后端 NPE 500，堆栈定位到 savePaperFromVM:105。同类操作在学科模块却是「静默返回成功」—— 同一系统两套错误处理`
